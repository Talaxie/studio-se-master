# Relational strategy — SQL Server, PostgreSQL, MySQL and Oracle

Available in `tMSSqlOutput`, `tPostgresqlOutput`, `tMysqlOutput` and
`tOracleOutput`, and through `tDBOutput` when the corresponding database is selected.
The existing component unifier exposes each database's parameters.
The generated writer has automated JDBC and live SQL Server order/rollback checks.
Live functional jobs also validate all four actions on PostgreSQL, MySQL and Oracle using shared connections. See [benchmark results](BENCHMARKS.md) for the measured comparisons.

## Configuration

1. Select **Defined by relational strategy column** as the data action.
2. Select the String column `relationalStrategy` in the incoming schema.
3. Mark the common lookup keys in the schema. At least one non-key SQL column is required.
4. Connect only the columns to write. Omit columns calculated or generated by SQL Server.

The strategy column is kept in the flow/reject schema, but omitted from all SQL,
including table creation. No separate per-operation column/key table is used.
Existing advanced field options and additional SQL columns are ignored in this mode.

| Value | Operation |
| --- | --- |
| `INSERT` | Insert all connected SQL columns, including keys |
| `UPDATE` | Update non-key columns using all schema keys |
| `DELETE` | Delete using all schema keys |
| `UPSERT` or `UPDATE_OR_INSERT` | Update; insert only when the update affects zero rows |

Values are trimmed and matched without case sensitivity. Null, empty and unknown
values follow Die on error / reject handling, with SQL state `RS001`. SQL errors
keep their original SQL state. Rejects retain the original strategy value.
An unmatched UPDATE or DELETE affects zero rows without being rejected.

Execution preserves input order and uses three reusable prepared statements.
Keys are not updated. Enable **Use batch size**, then set **Maximum relational
strategy batch size** in Advanced settings (default **50000**, positive Java integer
expression, context expressions accepted). This is independent of **Commit every**.

Batches require **Die on error** and no outgoing data connections (main or reject).
Otherwise execution falls back to per-row writes to preserve row/reject semantics.
Only consecutive INSERT, UPDATE or DELETE actions are batched. A change of action,
UPSERT, commit boundary, full batch, or end of input flushes the current batch.
UPSERT stays sequential because its UPDATE count determines whether to INSERT.

Batches require autocommit disabled. An owned connection disables autocommit and
commits at configured intervals, plus at normal completion; Commit every = 0 means
one final commit when batching is enabled. A shared connection must already have
autocommit disabled; the writer never commits or closes it. A SQL failure rolls
back the entire current transaction, including other work on a shared connection.
Already committed intervals remain committed. An upstream interruption also clears
the queued batch and rolls back, without replaying pending writes during cleanup.
Per-row mode retains the existing transaction owner/error behavior.

Affected-row counters use actual JDBC results. SUCCESS_NO_INFO commands are counted
separately in NB_LINE_BATCH_UNKNOWN, without inventing an affected-row count.
Counters report rows affected by the actual SQL operation. The existing connection
ownership and Commit every behavior are retained. UPSERT adds no intermediate commit;
it does not promise atomicity against concurrent writers.

The first version requires a fixed schema and sequential execution. Explicit
identity settings are rejected. All connected columns are inserted: a generated
identity supplied solely as a lookup key is therefore outside this first scope.
The SQL Server driver, constraints, triggers and transaction state still determine
whether execution succeeds; rejecting a row does not repair an aborted transaction.

## Automated checks

From `tdi-studio-se`, using Java 21 and dependencies already installed in `~/.m2`:

```sh
python3 dev/relational-strategy/verify.py
mvn -o -pl main/plugins/org.talend.designer.components.localprovider -DskipTests package
```

The first command parses component XML, compiles the four actual JET emitters,
generates and compiles jobs, and runs them against a JDBC test double. It checks
mixed actions on the same key, both upsert paths, invalid strategies, SQL errors,
reject contents, counters, nullable keys and statement cleanup after failure.
Batch tests cover limits 2/50000, invalid limit 0, action boundaries, end-of-input,
UPSERT ordering, both driver exception forms, upstream interruption, unknown
counts, shared ownership, autocommit guard, and owned commit intervals 0/2.
Additional generated jobs cover composite keys, dates and multiple NVARCHAR columns.
It compares generated code for all seven existing static modes against `HEAD`
(disregarding whitespace). It uses temporary files outside the checkout.

Run the generated writer on the existing SQL Server connection with:

```sh
RS_SQLSERVER_TESTS=1 python3 dev/relational-strategy/verify.py
```

Credentials are read from the existing strategy benchmark job, kept in memory and
passed through stdin. Only a session-local temporary table is written. It tests
mixed actions, repeated-key UPSERT, and full rollback with XACT_ABORT OFF/ON, at
batch limits 2 and 50000.

Before release,
verify Studio parameter persistence/reopening through tDBOutput, generated/default
columns omitted from the flow, table creation, commits/rollback on owned and shared
connections, query timeouts, and behavior with the intended SQL Server driver.

## PostgreSQL, MySQL and Oracle extension

The three new backends use the existing dialect managers, native connection setup,
identifier casing options, schema qualification and JDBC type bindings. Only the
relational-strategy action selects the new common dispatch/prepare/end templates
under `components/templates/DB/Output/RelationalStrategy*.inc.javajet`.
The existing static actions keep their original generated Java (verified against
HEAD, ignoring whitespace, including PostgreSQL native UPSERT and MySQL-specific actions).

The same contract applies: a String action column, common schema keys, connected
SQL columns only, INSERT/UPDATE/DELETE/UPSERT (UPDATE_OR_INSERT alias), batch limit
50000 by default, ordered consecutive-action batches, flush before action changes,
UPSERT/commit/end, and rollback of the current transaction on a fatal batch error.
The technical action column stays in main/reject flows and is excluded from SQL
and DDL. Dynamic schemas, parallel execution and spatial-processing options are
rejected explicitly in this mode. Advanced per-field options/additional columns
are ignored, as in the SQL Server implementation.

- **PostgreSQL:** quoted identifiers and the existing lowercase option are retained.
  Per-row error continuation uses a savepoint when autocommit is disabled, including
  when an existing saved batch option is true but batching falls back to row mode.
  Rollback to the savepoint lets a rejected row leave the transaction usable. Failure
  to create/recover the savepoint is fatal. Legacy SAVE_POINT settings are bypassed
  in this action because the new path manages its own savepoints.
- **MySQL:** an UPSERT UPDATE returning zero is followed by a bound lookup on the
  common keys, before any INSERT. This prevents a duplicate INSERT when the driver
  reports changed rows and an existing row already has the requested values.
  Standard JDBC batches work independently of the legacy MySQL batch-version gates.
  Batch mode checks that the target is an InnoDB base table before the first write;
  MyISAM and views with no verifiable engine are rejected for batch mode. Engine
  lookup and UPSERT lookups do not alter SQL input columns. A transactional engine
  is required for the rollback guarantee.
- **Oracle:** uses addBatch/executeBatch, not proprietary Oracle update batching.
  SUCCESS_NO_INFO is tracked by NB_LINE_BATCH_UNKNOWN without inventing affected-row
  totals. Invalid negative JDBC counts are fatal (also tightened for SQL Server).
  DATE/TIMESTAMP, timestamp with time zone, national character types, RAW, CLOB,
  BLOB and XMLTYPE reuse the native Oracle emitters/helpers and connection options.
  Generated/default columns are omitted by leaving them out of the connected schema.

MySQL/Oracle table actions remain available on shared connections, with the same
native DDL/DML behavior as the classic output. For CREATE/DROP/TRUNCATE actions,
an informational warning is displayed in the component properties and printed once
at component initialization. It warns that implicit commits may validate pending
work from other components on the shared connection. NONE and CLEAR (DELETE) do not
show this warning. The warning does not block or modify transaction handling.
Table creation/truncation precedes data writes; rollback of data does not promise
to undo DDL or any work already committed implicitly.
Connection failures and transaction-rollback SQL states are fatal, even when row
rejects are enabled; MySQL deadlock/lock-timeout errors are also fatal.

### Verification

```sh
python3 tdi-studio-se/dev/relational-strategy/verify_multi_db.py
python3 tdi-studio-se/dev/relational-strategy/verify.py
```

The first check compiles the actual 12 PostgreSQL/MySQL/Oracle JET emitters and
baseline emitters, then compiles and executes generated jobs against JDBC doubles.
It loads the real MySQL, Oracle and PostgreSQL type mappings from this checkout.
It covers shared-connection table actions and nonblocking DDL warnings, mixed action ordering, repeated-key UPSERT, final partial batches,
threshold/action flushes, both batch exception forms, rollback/no replay, upstream
interruptions, shared ownership, own-connection commit intervals 0/2, unknown and
invalid counts, PostgreSQL reject/savepoint recovery, MySQL unchanged-value UPSERT
and the nontransactional-engine guard. Compilation also covers composite/null-safe
keys, case options, dates, decimals, UUID, multiple character columns and Oracle
LOB/XML/time-zone bindings (using the locally cached Oracle JDBC library).
The second check protects the existing SQL Server implementation. No benchmarks
or live database writes are launched by these checks.

The three new backends have not been validated against live PostgreSQL, MySQL or
Oracle servers in this environment. Docker is installed but its daemon is not
running, and no test servers were connected for this change.

Primary references used for the database-specific behavior:

- MySQL Connector/J useAffectedRows: https://dev.mysql.com/doc/connector-j/en/connector-j-reference-configuration-properties.html
- Oracle JDBC standard batching: https://docs.oracle.com/en/database/oracle/oracle-database/18/jjdbc/performance-extensions.html

## Functional acceptance and benchmarks

The `testStrategy_MySQL`, `testStrategy_Oracle` and `testStrategy_PostgreSQL` jobs
passed INSERT, UPDATE, DELETE and both UPSERT branches with `actor_id` as the
common key and one shared connection with autocommit disabled. Each job checks
the complete expected result before commit; a fresh connection confirms the
committed values afterward. SQL Server has separate live order/rollback checks.

[BENCHMARKS.md](BENCHMARKS.md) records timings, percentage differences and limits
of the SQL Server and PostgreSQL/MySQL/Oracle campaigns. The latter validated
all 36 INSERT/UPDATE/DELETE cases at 10,000 and 100,000 rows with batch size 50,000.

Developer utilities under `benchmark/`, `multi-db-benchmark/`, `shared-tests/` and
`transaction-tests/` retain local workspace/fixture paths used for these runs.
Adjust them to your environment before preparing or running live jobs; these
utilities can reset only the dedicated test tables described in their protocol.
Do not commit generated Java jobs, credentials, exports, compiled classes or logs.
